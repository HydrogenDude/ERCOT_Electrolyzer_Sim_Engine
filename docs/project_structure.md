Each top-level directory has a single, well-defined responsibility,
described below.

---

## `configs/` — Simulation and Experiment Configuration

The `configs/` directory contains all configuration information that
defines **what simulations are run**, independently of the simulation
engine itself.

Changing files here changes the *experiment*, not the implementation.

### Subdirectories

- **`system/`**  
  Global system-level settings such as:
  - electrolyzer system parameters
  - time resolution and simulation horizon
  - fixed modeling assumptions

- **`scenarios/`**  
  Definitions of different operating or grid scenarios, such as:
  - renewable penetration levels
  - price regimes
  - stress-test or extreme-event cases

- **`paper_cases/`**  
  Configuration sets used specifically for results reported in the paper.
  These cases should be stable, versioned, and directly referenced by
  reproduction scripts.

**Guiding rule:**  
If changing a value alters *what experiment is being run*, it belongs in
`configs/`.

---

## `data/` — Model Input Data

The `data/` directory stores input data required by the model.

### Subdirectories

- **`inputs/`**  
  Input datasets used by the simulation, such as:
  - grid demand or generation profiles
  - price signals
  - externally generated CSV files (e.g., controller case definitions)

Large raw data archives or proprietary datasets should generally NOT be
committed. This folder should contain only what is necessary to reproduce
published results or demonstrate example runs.

---

## `docs/` — Developer and Workflow Documentation

The `docs/` directory contains internal documentation describing
development practices, workflows, and project organization.

### Subdirectories

- **`workflows/`**  
  Documentation covering workflows such as:
  - git usage and branching conventions
  - analysis and simulation workflows

This directory documents *how the project is worked on*, not the
scientific model itself.

---

## `main/` — Core Simulation Code

The `main/` directory contains the implementation of the simulation
engine.

Code here defines **how the model works**, including:
- the time-stepping logic,
- electrolyzer state machines,
- controller logic,
- and supporting physical or numerical models.

### Subdirectories

- **`matlab/`**  
  MATLAB-based simulation code.

- **`python/`**  
  Python code that is part of the core workflow, such as deterministic
  generation of simulation cases or tightly coupled preprocessing.

**Boundary rule:**  
Code in `main/` affects model behavior. General utilities belong in
`tools/`.

---

## `outputs/` — Generated Results

The `outputs/` directory stores artifacts generated by simulations or
post-processing. These files are typically not tracked by git and can
always be regenerated.

### Subdirectories

- **`results/`** — numerical simulation outputs  
- **`figures/`** — plots and visualizations  
- **`tables/`** — aggregated or summary data tables  

Empty directories may be preserved using placeholder files (e.g.,
`.gitkeep`).

---

## `scripts/` — User-Facing Entry Points

The `scripts/` directory contains high-level scripts that users are
expected to run directly.

Typical uses include:
- reproducing paper results,
- running a minimal example simulation,
- executing batch runs of configuration sets.

Scripts here should orchestrate workflows rather than implement core
model logic.

---

## `paper/` — Manuscript-Related Materials

The `paper/` directory contains material used during manuscript
preparation, such as:
- figure-to-script mapping notes,
- draft method text,
- reviewer response notes.

Nothing in this directory is required to run the model.

---

## `supplemental/` — Paper Supplementary Materials

The `supplemental/` directory contains formal supplementary materials
referenced by the paper.

Examples include:
- detailed state-machine definitions,
- extended controller logic tables,
- parameter lists and bounds,
- sensitivity analyses.

Files in this directory are intended to be referenced explicitly in the
paper (e.g., Supplement S1, S2, etc.) and should remain stable after
submission.

---

## `tools/` — Auxiliary Utilities and Tooling

The `tools/` directory contains general-purpose utilities that improve
productivity or help inspect results, but do not affect simulation
behavior.

### Subdirectories

- **`inspection/`**  
  Tools for inspecting the project structure or data, such as directory
  tree viewers or metadata analyzers.

- **`visualization/`**  
  Tools for plotting or visually exploring numerical data and timelines.

- **`formatting/`**  
  Tools for converting or packaging artifacts, such as combining scripts
  into PDFs or formatting reports.

- **`misc/`**  
  Small or one-off utilities that do not yet fit another category.

Tools are optional and should never be required to run the simulation.

---

## Top-Level Files

- **`README.md`**  
  High-level description of the project, its purpose, and instructions for
  reproducing results.

- **`.gitignore`**  
  Defines which generated files and folders are excluded from version
  control.

---

## Design Philosophy Summary

This repository structure is designed to:
- separate scientific logic from tooling,
- ensure reproducibility of results,
- support publication and review,
- and allow long-term extension without refactoring.

When adding new files, ask:
> “Does this define the experiment, implement the model, support the
> paper, or help me work more efficiently?”

The answer determines the correct location.
